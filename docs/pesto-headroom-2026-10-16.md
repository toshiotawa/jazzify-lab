# PESTOの推論負荷・音声欠落対策

2026-10-16。比較元: stg `4ba3917519d000d4b187ad5de053e45660db346c`。

## 変更

固定入力のCQT前処理にある8個のConvを、同じ係数の行列積（Gemm）と形状変換へ置き換えた。各窓の入力幅とカーネル幅が一致し、時刻方向の出力が1点なので成立する。WASMの汎用Conv経路を避け、推論の余裕を確保する。モデルの量子化・再学習はしていない。

学習済み係数・refill・PCM履歴3976サンプル・モデル入力240サンプル・単一WASMスレッド・5/10/20ms周期・オンセット判定は維持。Workletの転送2枠・待機上限40msも維持する。音声を余計に捨てる、省略回数を増やす、上限を広げて欠落だけを隠す変更はない。

新モデルは既存ONNXから差分で初期化時だけ復元する。モデルIDと差分URLを `compact-v2` に更新し、immutable配信済みのv1はそのまま保持。元のONNXとiOSモデルは変更しない。生成用Pythonはプレイ中には使わない。

診断は、これまで固定値0だった前処理時間を実測し、推論時間から分離。取り込み側の転送待ちとWorker内の待ちも別々に出力する。MessagePort内の配送待ち時間はこれらに含まれない。検証ブラウザでは原音終了時刻とmonitor受信時のAudioContext時計の差をpipelineLagとして測り、推論・キューだけでは見えない配送遅延も含めた下流の遅れを確認する。実デバイスの入力遅延ではない。

## 出力同等性

- `verify-pesto-web-model.mjs`: 実WASM、旧compact-v1と新v2を交互に2,400フレーム実行。持続音・音程変更・倍音・小音量・無音・ノイズ・インパルスとcache初期化を含む。最大差はMIDI 0.0000267（約0.00267セント）、confidence 0.00000185、volume 0.0000611。PCM cacheは厳密一致。いずれも既存の許容差内。元ONNXとの比較も成功した。
- 同じSalamander/Feltピアノ音声の147条件を10msで、同じ28条件を5ms・20msで再実行。合計203実行・40,038観測。生ピッチ差は最大約0.00496セント。発音・消音の全イベント、音番号、通知した原音位置、遡及onset時刻が修正前と完全一致。検出数・余分な発音・遅延・RPAも維持した。
- `verify-pesto-gap-recovery.mjs`: 実WASMで3,200フレーム、保持2,658・欠落542・履歴復元68回。復元後のprediction/confidence/volume/cacheは欠落のない参照と厳密一致。

10msの音替わり64音は両版とも64/64、余分な発音13回、通知原音位置の遅延中央値40ms。今回の目的は負荷改善であり、同音連打などの既存の認識課題を直した結果ではない。

## 単独WASMの時間比較

他の検証を並走させず、実配信v1/v2を各2,400回、実行順を交互にして比較。最初の100回を時間集計から除外。Node v24.19.0、onnxruntime-web 1.20.0、単一スレッドWASM。

| 推論時間 | compact-v1 | compact-v2 |
| --- | ---: | ---: |
| 中央値 | 5.94ms | 3.06ms |
| p95 | 6.65ms | 3.54ms |

中央値は約48%短縮。ただし共有CPUの環境依存値であり、利用端末の時間を保証する値ではない。

## 検証環境と再現

本番ビルドのAudioWorklet → MessagePort → Worker → 単一スレッドWASMを使用。Linux x86_64、Headless Chromium 153、crossOriginIsolated=false。前回と同じ4音声（Salamander/Feltの250ms音替わり・200ms同音連打）の10.8秒ループ。48kHz、感度5、安定判定4、fastResponse=false、正解音補助なし。音声SHA-256は集計JSONに記録。

再現コマンドは `scripts/pesto/README.md` のcompact-v2節を参照。ブラウザ用の `benchmark-pesto-headroom.mjs` は試行ごとにWorker/AudioContextを作り直し、終了時に解放する。競合負荷は検証サーバーが返すWorkerにのみ追加し、配信コードには入らない。全テスト・ビルド・モデル同等性検証が終了してから、ブラウザ試験を1試行ずつ実行した。

集計値と診断: [pesto-headroom-2026-10-16.json](./pesto-headroom-2026-10-16.json)。診断p95は末尾128観測。windowsは約300msごとのsnapshot統計の分布であり、全推論を直接集計したp95ではない。オフラインの通知遅延は原音時計、ブラウザの通知遅延はメインスレッド受信時のAudioContext時計であり、定義が違う。

## チェック・実行時負荷

型チェック成功、lintエラー0・警告0、315ファイル・2,385テスト成功、本番ビルド成功。ts-pruneは修正前と行番号を正規化して比較し、新規指摘なし（既存指摘は対象外）。ビルドには既存のBrowserslist・ONNX依存内eval・チャンクサイズ等の警告が残る。

新しい描画フレーム処理・本番タイマー/ポーリング・高頻度React state・音声フレーム内の配列生成は追加していない。既存音声処理内で診断の数値3項目を既存オブジェクトへ代入し、低頻度snapshot時のみ最大128要素の集計配列を追加する。モデル変換はオフライン、復元とハッシュ検証は初期化時だけ。配信モデルのサイズ増は約1.5KB、差分ファイルの増加は約2KB。

実マイク・Apollo・Safari・M2・ゲーム描画を含む確認は未実施。CPU負荷が原因の欠落を減らす対策であり、上流の入力レベル低下を説明・解消したことにはならない。

## 10ms・通常の2分入力

今回の修正前再測定は欠落0、新版の単独最終試行も欠落0。以前の「旧版で計70ms欠落」は今回の通常試行では再現しなかったので、70→0を今回の因果的な改善量として扱わない。

新版の初回通常試行では35msの欠落を1回観測した。この試行にはオフライン音声参照の結果集計との短時間の重複があったため、単独の性能試行から除外して再実行した。初回データもJSON内に保持する。30秒の5ms予備試行でも70msの欠落が2回あった。単独最終試行の0欠落を、環境を問わず欠落しない保証には使わない。

| 項目 | v1・通常 | v2・通常最終 |
| --- | ---: | ---: |
| PCM欠落 / 不連続 | 0 / 0回 | 0 / 0回 |
| 正しい音の通知 | 202/444 | 202/444 |
| noteOn総数 | 248 | 248 |
| 通知遅延・中央値 | 40.00ms | 38.00ms |
| 通知遅延・p95 | 49.33ms | 47.33ms |

補助なし同音連打を含むため、202/444は既存の取りこぼしを含む。モデル処理時間が短くなっても、基本周波数を推定するための音声窓の長さは変わらない。

## 10ms・競合負荷を加えた2分入力

両版で、同じWorker内に50msごと20msのbusy処理を追加した。別アプリ等の実機負荷を再現したものではなく、同じ条件で処理余裕を比較する検証専用の競合。各版を120秒、並走させずに測定した。

| 項目 | v1 | v2 |
| --- | ---: | ---: |
| PCM欠落合計 | 14,385ms | 105ms |
| 欠落回数 | 411 | 3 |
| 原音終了→monitor受信の遅れ・p95 | 54.67ms | 30.67ms |
| queueAge p95のsnapshot間中央値 | 30.00ms | 14.67ms |
| エラー / モデルreset | 0 / 0 | 0 / 0 |

この人工負荷下の欠落量は約99.3%減ったが、3回は残った。新版の待ち時間は主に取り込み側（snapshot間中央値14.67ms）、Worker内の待ちは計測分解能程度（中央値0、最大snapshot p95が0.1ms）。前処理p95も多くの窓で計測分解能以下。キュー上限を増やした結果ではない。

この試験では欠落によって観測位相と連打判定も変わる。正しい音の通知数はv1が239、v2が202、noteOn総数は315→247だった。負荷試験の通知数を精度の優劣に用いず、入力を欠落させない203条件の比較でモデル出力・イベントの維持を確認している。

## 既定5ms・通常の2分入力

同じ4音声・120秒、追加の競合処理なし。旧版と新版を単独で順に測定した。どちらも設定は既定5msのまま。
